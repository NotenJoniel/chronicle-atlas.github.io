# Chronicle Atlas — 実装課題・リファクタバックログ

> このファイルはAIエージェントが作業開始時に参照するための技術課題リストです。
> Claude 5によるレビュー結果（2026-08-04）をベースに、オーナー同意済みの項目を整理しています。

---

## ⚠️ 最重要方針：論理的統合 + 物理的分割

**「1つのデータベースにまとめる」≠「1つのファイルにまとめる」**

現在のサブプロジェクト方式（各ディレクトリに `data.js` を置く増殖パターン）は維持する。
やるべきことは**スキーマ（フィールド名・構造の取り決め）の共通化**であり、ファイルの物理統合ではない。

### 目標ディレクトリ構造（将来像）

```
data/
  schema.json          ← 共通の型定義（小さい。これが「統合」の実体）
  index.json           ← 各タイムラインのメタ情報だけ（ID・名称・期間・件数）
  timelines/
    china-warring-states.json
    chu-han.json
    han.json
    three-kingdoms.json
    rome-empire.json
    japan-sengoku.json
```

### なぜこの構造か

- **AIのコストはファイル単位**: 三国時代の編集時に読むのは `schema.json` + `three-kingdoms.json` だけ。他のタイムラインは一切コンテキストに入らない。
- **機能の恩恵はスキーマ単位**: 全ファイルが同じフィールド名で書かれているので、横串ビューはビルド時にマージするだけで成立。
- **コスト感の実数**: 出来事1件 ≒ 250〜400トークン。150件で4〜6万トークン。1ファイル200〜300件を超えたら期間で分割（例: `han-western.json` / `han-eastern.json`）。

### 🚨 最大の警戒対象：スキーマドリフト

サブプロジェクトを独立に増やすと、あるタイムラインは `year`、別のは `date`、また別のは `年代` のように**微妙に違う形で書かれていく**。個別に見れば全部正しく動くが、横串ビューを作ろうとした瞬間に破綻する。20本溜まってからの移行は「全ファイルを読んで直す」コンテキスト爆発そのもの。

**→ 先にスキーマを決めておくことが、将来の大規模リファクタを回避する投資。**

---

## 🔴 今決めておくべきこと（安いうちに）

### 1. フィールド名と型の統一
- 年の持ち方（`year` フィールド、紀元前は負数 `-221` など）
- 紀元前の表現方法
- 確度フラグ（`certainty: "confirmed" | "disputed" | "approximate"`）
- 分類タグの語彙（全時代共通のカテゴリ定義）

### 2. IDの命名規則
- ファイルを開かずに参照できる形: `three-kingdoms/battle-of-red-cliffs`
- タイムライン横断でユニークなID体系

### 3. バリデーションスクリプト
- CIで型チェック → AIが生成したデータを人間が読んで検証する必要がなくなる
- これもコンテキスト節約になる

### 4. 整形済みJSON
- minify禁止（diffが壊れて部分編集ができなくなる）
- Pretty-printで保存

> **NOTE**: 固有名詞の統一辞書のようなものは後からでも十分間に合うので今は不要。

## 🟡 設計課題（優先度：中）

### 5. 分類タグの全時代共通化
- **現状**: 各サブプロジェクトで独自のカテゴリ定義（戦国は「戦・政・人・城」、三国志は別定義など）
- **方針**: 全時代共通の分類軸を定義し、「政変だけ追う」「合戦だけ追う」といったフィルタを全時代で統一的に機能させる
- **効果**: 単なる年表から「歴史データベース」に進化

### 6. 年代の扱い方針
- **課題**:
  - 紀元前の年数え
  - ユリウス暦とグレゴリオ暦のずれ
  - 和暦・元号との対応
  - 諸説ある年代の表示（例：北条早雲の伊豆討ち入り 1493年説 vs 1491年説）
- **方針**: データ側に「確度」フィールドを持たせ、UIで点線や補足表示で区別
- **効果**: 歴史好きからの信頼度が大幅向上

### 7. JavaScript描画によるSEO問題
- **現状**: タイムラインの中身はJS描画のため、HTMLソースに含まれない
- **影響**: 検索エンジンのクローラ、SNSカード生成、外部ツールからの参照で年表データが「無いもの」として扱われる
- **対策案**:
  - ビルド時に静的HTMLを生成（SSG化）
  - 最低限: 各タイムラインページに主要テキストをサーバー側で埋め込む
- **追加施策**: 個々の出来事にアンカーリンク（例: `/three-kingdoms#red-cliffs`）を振る → 共有性と検索流入が大幅改善

## 🟢 コンテンツ拡充ロードマップ（優先度順）

### 最優先：漢帝国（前漢・後漢）
- 既存3本の中国系タイムライン（戦国→楚漢→三国）をつなげる最重要ピース
- 楚漢戦争終結（BC202）〜 三国時代開始（AD184）の**約400年が空白**
- 武帝の対匈奴戦争、張騫の西域派遣、王莽の新、光武帝、党錮の禁→黄巾の乱

### 次点：ローマ共和政
- ローマ帝国編の前史を埋める
- ポエニ戦争、グラックス兄弟、カエサルまで
- 中国の戦国時代と時期が重なり「同じ頃、地中海と黄河流域で何が起きていたか」の比較が成立

### その後の展開候補
| 候補 | 理由 |
|---|---|
| **モンゴル帝国** | ユーラシアを東西に貫き、中国系とヨーロッパ系タイムラインの「結節点」として機能 |
| **ヘレニズム時代**（アレクサンドロス） | 中国戦国時代と同時代、全く別の論理で動く対比が劇的 |
| **大航海時代・宗教改革** | 日本の戦国時代とセットにすることで「鉄砲伝来やザビエル来日の世界史的文脈」が線でつながる |

### 日本の戦国時代（実装済み）への補足
- 既存コンテンツと800年以上離れるため「単発の島」になっている
- 同時代のヨーロッパ（大航海時代、宗教改革、ハプスブルク家）をセットで追加すると差別化が強化される

## 🔵 目玉機能候補

### 横串ビュー（同時代比較）
- **概要**: 複数文明を同一の時間軸に重ねて表示する機能
- **意義**: 個別の年表は他サイトにもあるが、複数文明の同時代比較ができるサイトは希少
- **効果**: サイト名「Atlas」のコンセプトが最も活きる機能
- **前提**: データとUIの分離（スキーマ共通化）が完了していること

### 共通アーキテクチャ（現行）
- 各サブプロジェクトは `data.js` + `app.js` + `styles.css` + `index.html` の4ファイル構成
- `data.js` が `window.appData` にデータをエクスポートし、`app.js` が参照
- トップページ `index.html` のデータ配列で `link` / `linked:true` を設定してリンク有効化
- 勢力図は `main-layout` の `height:calc(100vh - 140px); overflow:hidden` + 各カラム独立スクロールで実現
- **新規サブプロジェクト作成時は、既存の動作済みプロジェクトのコードをテンプレートとして忠実に参照すること**
