# Chronicle Atlas — 設計思想・アーキテクチャ方針

> **このドキュメントの位置づけ**
> `BACKLOG.md` が「何をやるか（タスク）」を扱うのに対し、本書は「**なぜそう作るか（判断基準）**」を扱う。
> AIエージェントは、実装判断に迷ったとき・新しいタイムラインを追加するとき・既存コードを変更するときに本書を参照すること。
> タスクは消化されれば消えるが、本書の原則は残る。**原則と実装が食い違ったら、実装を直す。**

---

## 1. プロダクトの目的（不変）

**世界史のタイムラインを視覚的に分かりやすく表現し、「同じ時代に各地域で何が起きていたか」を比較しながら確認でき、歴史を楽しめるサイトをつくる。**

この一文が全ての判断の上位にある。以下は、そこから直接導かれる態度：

| 目的 | 導かれる態度 |
|---|---|
| **視覚的に分かりやすく** | 年表は「読む文書」ではなく「見る地図」。テキストの網羅性より、時間軸上の位置関係が一目で分かることを優先する |
| **同時代を比較できる** | 全タイムラインが**同一の時間軸**に載ること。これは機能ではなく前提条件 |
| **歴史を楽しめる** | 正確さは信頼の土台だが、目的ではない。逸話（`historyTrivia`）や人物のつながりが「面白さ」を担う |

> ⚠️ 「網羅的な歴史事典」を作ろうとしないこと。それは Wikipedia の仕事であり、本サイトは `wikiLinks` でそこに委譲している。
> 本サイトの価値は**選別と配置**にある。出来事を増やすより、時間軸上の見え方を良くする方が目的に近い。

## 2. North Star：横串ビュー（同時代比較）

最終到達点は、**複数文明を同一の時間軸に重ねて表示するビュー**である。

```
        BC500      BC250       AD1        AD250      AD500
中国  ├─戦国────────┤楚漢├─漢王朝──────────┤三国──┤
欧州  ├─共和政ローマ──────────┤ローマ帝国──────────────┤
日本                                                      … (AD1467〜)
```

- 個別の年表は他サイトにもある。**複数文明の同時代比較ができるサイトは希少**であり、ここがサイト名「Atlas」の意味そのもの。
- したがって横串ビューは「いつか作る機能の一つ」ではなく、**他の全ての設計判断が従属する目的地**である。

### 横串ビューが全ての設計に課す、たった一つの問い

> ### 🧭 **「そのタイムラインを、そのタイムラインの存在を知らないコードで描画できるか？」**

横串ビューは、7本（将来は10本以上）のタイムラインを**一つの汎用コード**で同時に描く。
つまり「共和政ローマ用の分岐」「三国志だけの特別扱い」がコードに残っている限り、横串ビューは実装できない。

**新しい実装・変更を加えるとき、この問いにYESと言えるかを必ず確認すること。**
NOになる変更（時代名や勢力IDをコードに直書きする等）は、たとえ短期的に動いても**目的地から遠ざかる負債**である。

## 3. 中心原理：3層モデル

上の問いを構造として表現したものが、以下の3層である。

```
┌─────────────────────────────────────────────────┐
│ ① データ層   data/timelines/*.json               │
│   その時代に固有の情報「すべて」                  │
│   出来事・人物・勢力・時代区分・勢力図            │
│   ★ 表示のための設定もここに含む（後述）          │
├─────────────────────────────────────────────────┤
│ ② 契約層     data/schema.json + validate.js      │
│   全時代が従う共通の型・語彙                      │
│   ここが守られている限り、③は①を知らなくてよい    │
├─────────────────────────────────────────────────┤
│ ③ 描画層     */app.js, */styles.css              │
│   時代を一切知らない汎用コード                    │
│   「データが来たらこう描く」だけを記述            │
└─────────────────────────────────────────────────┘
```

### 各層の責務と禁止事項

**① データ層 — 「時代に固有のものは、すべてここ」**
- 固有名詞、年、説明文はもちろん、**その時代特有の表示設定もデータである**
  - 勢力の表示順（サイドバーの並び）
  - 勢力の色
  - 勢力図の凡例ラベル
  - 初期表示する年
- 判定基準：**「他の時代では違う値になるもの」は、すべてデータ層に属する。**

**② 契約層 — 「時代をまたぐ約束事」**
- フィールド名（camelCase）、型、共通カテゴリ語彙を固定する
- `node data/validate.js` が唯一の正解。**人間のレビューを型チェックの代わりにしない**
- スキーマを変えるときは、7本すべてを同時に更新し、validate を通してからコミットする

**③ 描画層 — 「時代の名前が一つも出てこないコード」**
- `if (timeline === 'three-kingdoms')` のような分岐は**禁止**
- `const factionOrder = ['roma', 'populares', ...]` のような直書きも**禁止**（＝データ層に属する情報の漏出）
- CSSクラス名に時代固有の勢力名を焼き込まない（`.map-roma` ではなく、データ由来の色をインラインで与える）

## 4. 不変条件（AIが壊してはいけないもの）

以下は、破ると横串ビューが成立しなくなる。**変更提案そのものを拒否すること。**

### 4-1. 年は整数、紀元前は負数

```json
{ "year": -260 }   // ✅ BC260
{ "year": "BC260" } // ❌
```

- **理由**: これが横串ビューの背骨。全時代を1本の数直線に載せる唯一の手段。
- `"BC260"` `"紀元前260年"` などの表示文字列は、整数から**その場で導出する派生物**であり、データではない。
- `fmtYear()` / `fmtYearJa()` が変換を担当する。データ側に表示用文字列を持たせない。

### 4-2. 分類カテゴリは全時代共通の4つ

`battle` / `politics` / `episode` / `death`

- **理由**: 「政変だけ追う」「合戦だけ追う」を**全時代横断で**機能させるため。時代ごとに独自カテゴリを作った瞬間、横串フィルタは死ぬ。
- 増やしたくなったら、それは「7本すべてに意味があるか？」を問うこと。一つの時代のためだけのカテゴリは追加しない。
- `validate.js` が非標準カテゴリをエラーにする（ガードは既に効いている）。

### 4-3. 統一フィールド名（camelCase）

`eraPhases` / `factions` / `categories` / `characters` / `events` / `mapSnapshots` / `wikiLinks`

- **理由**: 横串ビューはビルド時に7本をマージするだけで成立する必要がある。フィールド名がずれると、マージのたびに変換表が必要になる。
- 🚨 **スキーマドリフトが最大の警戒対象。** 新規タイムライン追加時は、必ず `data/schema.json` と既存JSONを参照してから書き始める。

### 4-4. JSONはPretty-print（minify禁止）

- **理由**: diffが壊れると、AIによる部分編集ができなくなり、毎回ファイル全体の書き換えが必要になる（＝コスト爆発）。

### 4-5. Git運用

1. 作業は **`develop` ブランチ**
2. ブラウザで動作確認 → ユーザーに報告
3. **ユーザー承認後**に `main` へマージ（`main` = 本番 GitHub Pages）

> **絶対に未確認のコードを `main` にプッシュしない。**

## 5. コスト設計（AIが作り続けられる構造）

このサイトはAIが継続的に育てる前提で設計されている。**コンテキストコストは機能要件である。**

- **原則: AIのコストはファイル単位、機能の恩恵はスキーマ単位**
  三国時代を編集するとき読むのは `schema.json` + `three-kingdoms.json` だけ。他6本はコンテキストに入らない。
  それでいて全ファイルが同じ構造なので、横串ビューはマージするだけで成立する。
- **実数感**: 出来事1件 ≒ 250〜400トークン。1ファイル200〜300件を超えたら期間で分割する（例: `han-western.json` / `han-eastern.json`）。
- **横串ビューへの含意**: 7本の合計は既に約630KB。横串ビューが全ファイルを実データのまま読むのは筋が悪い。
  → **ビルド時に軽量ダイジェスト**（`year` / `title` / `category` / `timelineId` / 詳細ページへのアンカー）を生成し、横串ビューはそれだけを読む設計にすること。

## 7. 横串ビューまでのギャップ（優先度順）

現状、**データ層・描画層ともに準備完了。G1〜G4・G7まで完了し、横串ビュー（俯瞰・詳細比較の両レベル）は実証済み。残る課題はG5〜G6とコンテンツ拡充。**

### ✅ G1. IDのグローバル一意化 【対応済み 2026-08-05】

```
DUP event: e_actium      … roman-republic.json と roman-empire.json の両方に存在
DUP char:  c_cleopatra   … 同上
```

- **なぜ致命的か**: 横串ビューは7本をマージする。IDが衝突すると、どちらかが静かに消えるか上書きされる。
- 上記2件は内容を確認済み。事故的コピペではなく、**意図的な重複**（BC31年のアクティウムの海戦とクレオパトラは、共和政の終わりと帝政の始まり両方の物語の境界イベントとして、別内容で記述されている）。したがってデータの削除・統合はしない。
- `validate.js` に**横断重複チェックを追加済み**（`node data/validate.js` 実行時、`📋 Cross-file ID uniqueness` セクションに warning として出力される。境界年代の意図的な重複が正当なケースのため、エラーではなく警告扱い）。
- **横串マージ時の名前空間化規約**: 横串ビュー等でタイムラインをマージする処理を実装する際は、キーを必ず `${timelineId}::${localId}`（例: `roman-empire::e_actium`）の形で名前空間化すること。個別ファイル内のIDはそのまま維持し、マージ層でのみ変換する。JSON内部のIDを `roman-empire/e_actium` のようにファイル側で書き換える必要はない。

### ✅ G2. 時代固有の設定をコードからデータへ 【完了 2026-08-05】

`app.js` / `styles.css` に埋まっていた「データであるべきもの」はすべてデータ層に移した：

| 埋まっていたもの | 移行先 |
|---|---|
| 勢力の表示順 `factionOrder` | `factions{}` のJSON宣言順から導出 |
| 勢力図の凡例ラベル | `factions[].name` |
| 初期表示年 `renderMap(-200)` | `mapSnapshots[0].year` |
| 勢力の色（`.map-roma` 等のCSSクラス） | `factions[].color` / `colorLight`（JSがインラインstyleで適用） |
| three-kingdomsの地図固定レイアウト（`MAP_LAYOUT`） | `meta.mapLayout` |
| 地図の列数計算式（3パターンあった） | `meta.mapColumnRules` |
| 旧世代3本の静的フィルタボタン（`index.html`直書き） | 全7本で`renderFactionFilters()`/`renderCategoryFilters()`による動的生成に統一 |
| ヘッダー文言・検索placeholder・モーダル見出し等 | `meta.title`/`headerTitle`/`searchPlaceholder`/`descLabel`等 |

地図専用の疑似勢力（董卓・袁紹・劉表・劉璋・係争地など）は `mapOnly:true` フラグ付きで `factions{}` に正式登録済み（G1/G2の時点で対応済み）。G3の共通コードはこのデータをそのまま活用し、`renderFactionFilters` では `mapOnly` 勢力を除外して勢力フィルタボタンには出さないようにしている。

### ✅ G3. 描画層の重複解消 【完了 2026-08-05】

7本の `app.js`（各527〜557行、実質95%同一）と `styles.css` を統合した。

- **`shared/timeline-core.js`**: 全7本を駆動する単一エンジン。`body[data-timeline]` からタイムラインIDを読み、`data/timelines/<id>.json` を fetch して描画する。**タイムラインIDによる分岐は一切持たない** — `meta.mapLayout`/`mapColumnRules`/`historyDiff`/`historyOnly` 等、データの有無だけで挙動が変わる設計（③の判断基準を満たす）
- **`shared/timeline-core.css`**: 構造・レイアウト・モーダル・アニメーションを統一。ただし `.timeline`/`.event-card` の見た目（rail型＝左レール+ドット／flat型＝フラットカード）は `body[data-layout]` で切り替える2バリアントとして両方保持（時代ごとの意図的な個性として維持、統一しない）
- **`<name>/theme.css`**: 各タイムライン固有の配色（`--bg`/`--gold`等の基本テーマ変数）のみを残す。勢力色はテーマ変数ではなくJSONの`factions[].color`から直接インラインstyleで適用するため、`.map-<fid>`/`.tag-<fid>`というCSS変数駆動クラスは全廃した
- 各 `<name>/app.js` は削除。`<name>/index.html` が `shared/timeline-core.js` を直接読み込む
- three-kingdoms固有だった「正史/演義」表示機能（`historyOnly`バッジ、`historyDiff`セクション）は、特定タイムラインへの分岐ではなく「データにあれば汎用的に表示する」オプション機能として実装 — 将来他タイムラインでも使える
- 移行に伴い、three-kingdoms.jsonのevents配列にあった3箇所の年代順崩れ（ソート処理が無かったため）と、`syncActiveEvent`のyear=0無反応バグを修正
- Playwrightで7本すべてを検証（初期表示・フィルタ・検索・モーダル・地図・レイアウトバリアント・historyOnly/historyDiff）、コンソールエラー無し、イベント件数もデータと完全一致

### ✅ G4. 詳細比較モード 【完了 2026-08-05、🗑️ 2026-08-06 削除（G7に役割統合）】

> `compare/` は G7（横串ビュー）の追加後、「同時代比較」の役割が地域別俯瞰ビューに実質的に統合されたため削除した。以下は実装当時の設計記録として残す（レーン方式の衝突回避など、`cross/cross.js` が踏襲しているロジックの由来）。

当初は「`data/digest.json` をビルド時生成し、全7本を実データのまま読ませない」という設計を想定していたが、実装検討の結果**digest.jsonは不要と判明**した。詳細比較は2〜4個のタイムラインしか同時に扱わないため、選択したタイムラインの完全なJSON（各60〜130KB）を直接fetchすれば十分（説明文・人物情報等、比較に必要な情報も揃う）。トップページ全体（7本すべて・紀元前800年〜西暦1920年）への出来事分布表示のような将来拡張が出てきた場合に、その時点で改めてdigest.jsonの必要性を検討する。

- **`compare/index.html` + `compare.css` + `compare.js`** を新規作成。`compare/index.html?t=<id1>,<id2>[,<id3>,<id4>]` で2〜4個のタイムラインを選び、「列=タイムライン、縦軸=年」という共通の視覚言語（トップページの `.wt-grid`/`yearToY()` と同じ思想）で出来事を並べる
- 年軸は選択したタイムラインの**和集合**（積集合ではない — 一部期間が軸から消えて「何も無かった」と誤読させることを防ぐ）。重なり区間はハイライト帯で明示し、重ならない組み合わせは警告バナーを出す（ブロックはしない）
- 出来事は縮小カードを年座標に絶対配置する。**当初は貪欲法による縦の衝突回避+コネクタ線を採用していたが、密度が高い時代（短期間に出来事が集中）で縦位置が実際の年から際限なくずれていく問題が発覚し、レーン方式（同時期に重なる出来事はカレンダーアプリの予定表示のように横に並べる、最大4レーン）に変更した。これにより出来事は常に実際の年に一致した縦位置で描画され、密集は横方向の狭まりとして吸収される**
- `shared/timeline-core.js` に**1関数のみ追加**（`handleDeepLink()`、URLハッシュ `#e_xxx`/`#c_xxx` を見て該当モーダルを自動オープン）。既存7本の動作には一切影響しない。比較ビューの「元の年表で見る」ボタンがこれを使う
- モーダル等のCSSは `shared/timeline-core.css` をそのまま再利用。JSロジックは複製（`shared/`への抽出はYAGNIにより見送り）
- トップページの `nav-hint` バーに「🔀 同時代比較」への導線を追加

**出来事へのアンカーリンク**（`#e_xxx`）は上記の`handleDeepLink()`で実現済み。SEO向けの静的HTML化（BACKLOG項目9）は別課題として残る。

### ✅ G7. トップページ拡張（横串ビュー・地域別俯瞰） 【完了 2026-08-06】

DESIGN.md §7 冒頭で「①トップページの拡張（俯瞰レベル）」として未着手扱いだったものを、既存の `index.html` を一切変更せず**別ページ**として実装した。

- 実データ全件（9本・415件）をそのままfetchすると重いため、`data/build-digest.js` を新設し `data/digest.json`（出来事の年・タイトル・カテゴリ・場所・勢力色、人物一覧用の軽量な人物/勢力データ、共通カテゴリ定義）を生成する運用に切り替えた。§5で想定していた「トップページ全体への出来事分布表示のような将来拡張が出てきた場合にdigest.jsonの必要性を検討する」が現実になったケース。**タイムラインデータを編集したら `node data/build-digest.js` を再実行してコミットすること**

## 8. コンテンツ拡充の方針

**「出来事を増やす」より「時間軸の重なりを増やす」方が目的に近い。**
横串ビューの価値は、同じ時代に複数地域が並ぶことで生まれる。したがって拡充の優先度は「**既存タイムラインと時期が重なるか**」で決まる。

| 候補 | 重なる相手 | 状態 |
|---|---|---|
| **ヘレニズム時代**（アレクサンドロス） | 中国戦国時代・共和政ローマ | ✅ 実装済み（`hellenistic`） |
| **大航海時代・宗教改革** | 日本の戦国時代 | ✅ 実装済み（`age-of-exploration`、2026-08-06）。ザビエル来日（1549年）で`sengoku-japan`と交差する初のタイムライン |
| **モンゴル帝国** | （現状は孤立） | 未実装。ユーラシアを東西に貫き、中国系と欧州系の**結節点**になる唯一の候補 |

> `sengoku-japan`（AD1467〜）は`age-of-exploration`（1453〜1648）が加わったことで、他と800年以上離れた「単発の島」ではなくなった。横串ビューで日本列とヨーロッパ列が初めて同じ年軸上に実際の出来事として重なる（例: 1549年ザビエル来日 と 同年代のヨーロッパの宗教改革の動き）。

## 9. 判断に迷ったときの原則

新しい実装・変更に際して、上から順に適用する。

1. **横串ビューに近づくか？** 遠ざかる変更は、動いてもマージしない。
2. **時代を知らないコードで描けるか？** NOなら、時代固有の部分をデータ層へ動かす。
3. **他の時代では違う値になるか？** YESならそれはデータであり、コードに書いてはいけない。
4. **7本すべてに適用できるか？** 1本のための特別扱いは、7本目の特別扱いを呼ぶ。
5. **`validate.js` は通るか？** 通らないものはコミットしない。ルールを増やしたときは検証も増やす。
6. **次に触るAIは、このファイルだけ読めば分かるか？** 暗黙知はコンテキストコストとして跳ね返る。

## 10. 新規タイムライン追加の手順

1. `data/schema.json` と**既存の近い時代のJSON**を読む（例: 欧州なら `roman-republic.json`）
2. `data/timelines/<id>.json` を統一スキーマで作成
   - カテゴリは `battle` / `politics` / `episode` / `death` の4つのみ
   - 年は整数、紀元前は負数
   - IDは既存タイムラインと衝突しないこと（§7 G1）
   - `characters[].field`（統治/軍事/行政/思想/学術/芸術/経済の機能7分類＋公的機能を持たない人物用の`other`、必須）を全員に付与する。判断基準は `.agents/FIELD_TAXONOMY.md` を参照
3. `data/index.json` に登録（`id` / `name` / `region` / `startYear` / `endYear` / `dataFile` / `subProjectDir`）
4. `node data/validate.js` を実行し、**0 errors** を確認
5. サブプロジェクトのディレクトリを作成（既存プロジェクトをテンプレートとして参照）
6. トップ `index.html` にリンクを追加（`link` / `linked:true`）
7. `develop` にコミット → ブラウザで確認 → **ユーザー承認後**に `main`
